## 知识点 1：`std::vector` ——会自己长的数组

### 先想这个问题

你给房间指示牌开过伸缩尾巴：

```c
struct Room_area *p = malloc(sizeof(*p) + extra);
p->len = 10;
strcpy(p->instruction, "Gaming room");
free(p);
```

长度、分配、释放、会不会写爆，全是你的事。主机侧工具（仿真、日志、G-code 缓冲）其实只想要「一列能变长的 T」。

`std::vector<T>` 就是这块：堆上的动态数组，长大时自己 `realloc` 逻辑，离开作用域自己 `free`。RAII 版的伸缩尾巴。

### 它长什么样

```cpp
#include <vector>

void collect_pressures(std::vector<float> &buf, float sample)
{
    buf.push_back(sample);           /* 必要时自动扩容 */
}

float last_or_zero(const std::vector<float> &buf)
{
    if (buf.empty()) {
        return 0.0f;
    }
    return buf.back();
}

void dump(const std::vector<float> &buf)
{
    for (float v : buf) {
        (void)v;
    }
    /* 交给 C API 时：buf.data() 是连续内存，buf.size() 是元素个数 */
}
```

嵌入式固件里可能仍用静态数组——那是因为没有堆，或实时性不允许扩容。不是 `vector` 错了，是场景不让堆上场。主机侧仿真（你的 PID、LCD FSM 终端程序）用 `vector` 比手搓 `malloc` 更不容易漏。

`std::array<T, N>` 是定长数组的对象版：有 `size()`，能拷贝，越界可用 `.at()` 检查。比裸 `T buf[N]` 稍微像个类型。

### 本质

**`vector` 是元素连续、可扩容、析构时释放的序列容器。**

- **何时用到：** 长度运行期才知道、需要尾部追加、要交给算法去 `sort` / `find`。定长且很小，用 `array` 或栈上数组。
- **系统位置：** C++ 标准库（Standard Library）容器家族的默认序列。它是 RAII + 模板的展示柜：类型参数是元素，资源寿命跟对象走。
- **和柔性数组：** C 的尾巴挂在结构体最后一块内存上，布局自己定义；`vector` 把「指针 + 长度 + 容量」收进类型，布局不给你玩 `packed` 那套，换来安全。

## 知识点 2：`std::string` ——别再手搓 `\0`

### 先想这个问题

C 字符串是「约定以 `\0` 结尾的 `char` 数组」。忘写终结符、`strcpy` 写爆、长度和容量各算各的，是经典事故三件套。

`std::string` 把字符数据和长度绑成一个对象。拼接、比较、作为成员存放，都不再靠你维护 `\0`。

只读地看别人的字符串、又不想拷贝时，C++17 给了 `std::string_view`：不拥有内存，只是「从这里看这么长一段」。有点像 `const char *` + 长度，但是个正经类型。

### 它长什么样

```cpp
#include <string>
#include <string_view>

std::string state_name(int id)
{
    if (id == 0) {
        return "idle";
    }
    return "run";
}

bool is_g0(std::string_view line)
{
    /* 不拥有 line 的内存，调用方必须保证这段字符还活着 */
    return line.size() >= 2 && line[0] == 'G' && line[1] == '0';
}
```

和硬件协议、DMA 缓冲区打交道时，继续用裸 `uint8_t buf[]` 完全合理。`string` 解决的是 **文本在程序里的搬运**，不是寄存器布局。

### 本质

**`string` 拥有一块字符资源；`string_view` 只是对已有字符序列的只读观察。**

- **何时用到：** 日志、G-code 文本、文件路径、任何「人读的字符」。协议二进制帧不要硬塞进 `string`。
- **系统位置：** 标准库里的文本类型，同样是 RAII + 模板（`basic_string<char>`）的实例。
- **陷阱：** 不要用 `string_view` 指向马上死去的临时 `string`。观察者不能比被观察者活得更久——和悬空指针是同一类 bug。

## 知识点 3：`std::unique_ptr` ——一把伞只能一个人撑

### 先想这个问题

第 2 周的 `HeapBuffer` 是手写 RAII。标准库的答案是智能指针（smart pointer）：把「谁拥有这块堆内存」写进类型。

`std::unique_ptr<T>` 是独占所有权：同一时刻只有一个所有者。人走了（unique_ptr 析构），`delete` 自动发生。不能拷贝，只能移动（把伞递给下一个人，自己空手）。

`shared_ptr` 是共享所有权，带引用计数。本轮看见能认即可，默认先别用——固件和多数应用里独占就够，共享会把寿命变得难推理。

### 它长什么样

```cpp
#include <memory>

struct Sensor {
    float read();
};

void tick()
{
    auto sen = std::make_unique<Sensor>();  /* 分配 + 交给 unique_ptr */
    float p = sen->read();
    (void)p;
}   /* sen 离开作用域，Sensor 被 delete */
```

工厂函数 `std::make_unique` 比自己 `new` 再塞进去更不容易漏。读代码时看到 `unique_ptr<Foo>`，就把它想成「这是一个必有清理的 Foo 堆对象，而且只有我能删」。

没有堆的 MCU 工程里，你可能整周见不到它。那没问题——认得出就完成任务。

### 本质

**`unique_ptr` 用类型表达独占所有权，析构时释放被拥有的对象。**

- **何时用到：** 堆上对象需要明确的单一主人；工厂返回对象而不想让调用者记 `delete`；多态基类指针需要正确析构（配虚析构）。
- **系统位置：** 标准库 `<memory>`，RAII 在「单个堆对象」上的标准形态。容器管一批元素，`unique_ptr` 管一个对象。
- **和裸指针：** 裸指针不表达所有权（可能是观察）。接口若只是「借用一下」，用引用或裸指针；若是「送给你，由你释放」，用 `unique_ptr`。

## 知识点 4：`std::optional` ——合法的「现在没有」

### 先想这个问题

C 里表示「可能没有」通常是：指针为空、返回 `-1`、设一个 `bool valid`。压力传感器读失败、G-code 某字段没出现，都是这种。

`std::optional<T>`（C++17）把「有一枚 T，或什么都没有」做成类型。调用方必须先问有没有，再拿值——比偷偷返回 `0` 当失败更难装糊涂。

### 它长什么样

```cpp
#include <optional>

std::optional<float> read_pressure(bool ok, float value)
{
    if (!ok) {
        return std::nullopt;   /* 明确：没有读数 */
    }
    return value;
}

float or_default(std::optional<float> p)
{
    return p.value_or(0.0f);   /* 没有就用后备值 */
}
```

### 本质

**`optional<T>` 是带存在性标记的值类型，用来取代「魔法返回值」。**

- **何时用到：** 查找可能失败、配置项可缺省、传感器可读可失败。不是用来代替异常，也不是用来代替空指针的所有权。
- **系统位置：** 标准库的工具类型（utility type），和 `vector` 这类容器不同，它不管理堆上的一串元素，只给单个值加上「在/不在」。

## 知识点 5：`extern "C"` 与名字修饰 ——海关不给 C++ 整容

### 先想这个问题

第 1 周说过：C++ 允许三个都叫 `log_val` 的函数。链接器要区分它们，编译器就把符号名「整容」成一串带类型信息的怪名字，这叫 name mangling（名字修饰）。

C 不整容。`gcode_parse_line` 在 `.o` 里就叫这个名字（或加个下划线，取决于平台）。

一边 C++ 整容、一边 C 不整容，链接器就会报 `undefined reference`：两个人都觉得自己叫 `foo`，护照拼音却不一样。

`extern "C"` 是海关章：这块接口按 C 的规则导出，禁止整容。你在 `declaration.h` 里已经会写头文件防护，混编只是再包一层语言栏。

### 它长什么样

头文件同时给 C 和 C++ 看：

```cpp
#ifndef GCODE_H
#define GCODE_H

#ifdef __cplusplus
extern "C" {
#endif

void gcode_parse_line(const char *line);

#ifdef __cplusplus
}
#endif

#endif
```

- `__c__p____lusplus` 只在 C++ 编译器里有定义，C 编译器看不到 `extern "C"` 这种它不认识的语法。
- C++ 调用这份函数、C 定义它，或反过来，都能对上符号。
- 能塞进 `extern "C"` 的只能是普通函数，不能是成员函数、不能靠重载。要让 C 调 `class` 的方法，得再包一层 C 风格包装函数。

链接仍建议由 `g++` 出面（它会把 C++ 运行时带上）。`main` 若在 C++ 里，全局对象的构造才能在 `main` 前跑完。

### 本质

**`extern "C"` 关闭名字修饰并改用 C 调用约定，是两种语言的 ABI（Application Binary Interface，应用二进制接口）桥梁。**

- **何时用到：** C 库给 C++ 用、C++ 库要导出给 C、固件里 C 驱动 + C++ 业务。只要跨越 `.c` / `.cpp` 边界，先检查这枚章在不在。
- **系统位置：** 位于语言边界，不属于 OOP，也不属于标准库。它是链接模型的一部分。第 1 周的重载能存在，正是因为默认会 mangling；混编要把这条能力在边界上关掉。
- **排错口诀：** 编译过、链接说找不到函数 → 先看是不是一边 `extern "C"`、一边没有。

## 本周地图：标准库在 C++ 里站哪

```text
语言核心          你第 1～3 周学的：类型、引用、class、模板、虚函数
    └── RAII     第 2 周的原则
            └── 标准库类型    vector / string / unique_ptr / optional
链接边界          extern "C"、名字修饰
C 子集            仍可在 .cpp 里用：指针、struct、#ifdef、手动内存
```

标准库不是另一门语言。它是「用 class + 模板 + RAII 写好的一批常用类型」。你会 class 和 RAII，标准库只是认名字、查 cppreference。
