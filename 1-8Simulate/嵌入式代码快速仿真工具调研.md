# 嵌入式代码快速仿真工具调研

> 调研日期：2026-08-26  
>
> 目标：在没有实物硬件时，尽量直接使用已有源码或固件，快速验证程序输出、控制流程、异常处理和部分外设行为；不以手工绘制完整电路为前提。

## 1. 结论先行

不存在能够对“任意 MCU（Microcontroller Unit，微控制器）+ 任意外设”进行一键准确仿真的通用工具。仿真器必须知道 CPU、内存映射、中断控制器和外设寄存器的行为；目标芯片或开发板没有现成模型时，仍然需要补充平台描述或外设模型。

结合“代码优先、少搭电路、快速看到结果”的需求，建议按下面的顺序选择：

1. **ESP32、RP2040、Arduino 或受支持的 STM32：优先试 Wokwi。**  
   它最接近“编译后点击运行”。只验证串口、GPIO 或程序流程时，可以只放一个 MCU，不必绘制完整电路。缺点是芯片型号覆盖有限，商业项目和较多 CI（Continuous Integration，持续集成）时需要关注许可。
2. **Zephyr、RTOS（Real-Time Operating System，实时操作系统）、STM32/RISC-V 或多节点系统：优先试 Renode。**  
   它可以直接加载与真机相同的 ELF（Executable and Linkable Format，可执行与可链接格式）文件，自动化测试能力很强。已有开发板模型时较方便；没有模型时，配置成本会明显上升。
3. **仅验证算法、状态机、协议解析和异常分支：优先使用主机单元测试。**  
   Ceedling + Unity + CMock 的速度最快，也最适合每天运行。它不模拟真实芯片，但对大部分业务逻辑的验证比整机仿真更稳定。
4. **项目已经绑定厂商 IDE：直接检查其内置 Simulator。**  
   Keil µVision、MPLAB X SIM 和 IAR C-SPY 通常只需切换 Debug Driver（调试驱动），上手很快，但芯片、外设及许可证限制较强。
5. **QEMU 更适合已有受支持板型、系统启动和自动化验证。**  
   它不是任意 STM32 固件的通用替代品。官方明确说明，现有 Arm 板型只覆盖实际硬件中的一小部分，很多外设没有实现。

如果目前还没有固定 MCU，建议采用：

> **主机单元测试作为日常底座 + Wokwi 或 Renode 做固件级集成验证 + 最后用真机确认电气和时序。**

## 2. “快速验证”可以验证到什么程度

### 2.1 适合在无硬件环境中验证

- 算法、状态机、数据结构和协议解析；
- 任务创建、消息队列和大部分 RTOS 逻辑；
- 启动流程、异常处理和中断入口；
- 串口输出是否符合预期；
- 已被仿真器建模的 GPIO、UART、SPI、I²C、Timer 等外设；
- 固定输入、边界输入和错误注入；
- 回归测试、代码覆盖率和 CI 自动判定。

### 2.2 最终必须由真机确认

- 模拟电压、噪声、上拉电阻和信号完整性；
- 晶振偏差、真实中断延迟、总线争用和极限实时性；
- DMA（Direct Memory Access，直接内存访问）、Cache（缓存）及复杂并发问题；
- 厂商芯片勘误、未公开硬件行为和低功耗细节；
- 射频、功耗、温升、电机及机械负载；
- 仿真器尚未实现或实现不完整的外设。

因此，“仿真通过”表示软件逻辑在相应模型下通过，不等于产品已经完成硬件验证。

## 3. 工具对比

评分采用 1～5 分，属于基于本需求的主观工程评估：分数越高越适合“少配置、从代码快速看到结果”，不是工具本身的绝对排名。

| 工具/方案 | 代码启动便捷性 | 芯片/板级逼真度 | 外设覆盖 | 自动化测试 | Windows 体验 | 主要定位 |
| --- | --- | --- | --- | --- | --- | --- |
| Wokwi | 5 | 3 | 4 | 4 | 5 | 快速交互式固件仿真 |
| Renode | 3 | 4 | 4 | 5 | 4 | 可脚本化整机/多节点仿真 |
| QEMU | 3 | 3 | 2 | 5 | 3 | CPU、板型、系统启动与 CI |
| Arm FVP/AVH | 3 | 4 | 3 | 5 | 4 | Arm Cortex-M 参考平台 |
| Keil µVision Simulator | 5 | 3 | 3 | 3 | 5 | Keil 项目交互调试 |
| MPLAB X SIM | 5 | 3 | 3 | 4 | 4 | Microchip MCU 仿真 |
| IAR C-SPY Simulator | 5 | 2 | 2 | 3 | 5 | 程序逻辑和指令级调试 |
| Ceedling/Unity/CMock | 4 | 1 | 1 | 5 | 4 | 与硬件解耦的 C 单元测试 |
| Zephyr native_sim | 4 | 1 | 2 | 5 | 2 | Zephyr 应用主机原生运行 |

### 3.1 Wokwi

**特点**

- 支持 ARM、AVR、RISC-V 和 Xtensa 架构；
- 官方列出的 MCU 包括多种 ESP32、RP2040、ATmega，以及少量 STM32 型号；
- 可以在浏览器或 VS Code 中启动，并支持 PlatformIO、ESP-IDF、Zephyr、Pi Pico SDK、Arduino CLI、MicroPython 等工程；
- CLI 可以设置超时、检查串口文本并接入 GitHub Actions；
- 支持虚拟传感器、显示器、按键、逻辑分析仪和自定义芯片。

**是否需要画电路**

通常需要 `diagram.json` 描述 MCU 与器件，但这不是必须手工绘制完整原理图。只测试 MCU 和串口输出时，可以使用只包含 MCU 的最小配置。对于 ESP-IDF 6.0 及以上版本，`idf-wokwi` 可隐式生成配置，进一步减少准备工作。

**便捷性评价**

- 已支持的芯片：很方便，最接近本需求；
- 未支持的具体芯片：不能因为 CPU 内核相同就认为寄存器和外设兼容；
- 私有或商业项目：VS Code 扩展需要商业许可；价格和分钟数会变化，应在采用前查看官方页面；
- CLI/CI 由云端模拟服务器执行，涉及不能上传固件的项目时需要先确认合规要求。

**适合**

- ESP32、RP2040、Arduino；
- Wokwi 已明确支持的 STM32；
- 需要快速观察串口、GPIO、显示器或按键交互；
- 教学、原型和中小规模自动化测试。

### 3.2 Renode

**特点**

- 开源，由 Antmicro 维护；
- 支持 Cortex-A/R/M、RISC-V、Xtensa、MSP430X 等架构；
- 可直接加载与真机相同的 ELF、HEX 或 BIN 固件；
- 使用 `.repl` 描述平台，使用 `.resc` 封装重复启动流程；
- 支持 UART、Ethernet、GDB（GNU Debugger，GNU 调试器）、日志、执行跟踪、多节点和确定性虚拟时间；
- 与 Robot Framework 集成，可在 CI 中断言串口输出、注入输入，并保存失败快照。

**是否需要画电路**

不需要画原理图。若目标开发板已有模型，只需选择平台并加载固件。若没有模型，则要编写文本形式的平台描述，或者实现缺失的外设模型。它省去了“画电路”，却不会神奇地省去“描述硬件”。

**最小运行思路**

```text
mach create
machine LoadPlatformDescription @platforms/boards/目标开发板.repl
sysbus LoadELF @build/firmware.elf
showAnalyzer sysbus.uart
start
```

这些命令通常保存为 `.resc` 脚本，之后即可一条命令重复运行。

**便捷性评价**

- 有现成板型：中等偏方便；
- 芯片基本匹配但内存或外设不同：需要修改 `.repl`；
- 外设模型缺失：学习和开发成本较高；
- 自动化、可重复性和复杂系统测试能力强于一般 GUI Simulator。

**适合**

- Zephyr、FreeRTOS 等 RTOS 项目；
- STM32、RISC-V 和 IoT 固件；
- 多 MCU、多节点和网络协议测试；
- 希望长期建立固件 CI 的团队。

### 3.3 QEMU

**特点**

- 开源、命令行成熟、容易接入 CI；
- Arm System Emulator 支持 Cortex-M0、M4、M33 等 M-profile CPU；
- 能直接加载固件，并通过 GDB Stub（GDB 远程调试桩）设置断点、查看寄存器和内存；
- Semihosting（半主机）可以把固件输出转到主机终端。

**关键限制**

- 必须选择已经实现的 `machine`，没有通用的“任意 Cortex-M 芯片”模式；
- 官方明确指出，即使已有大量 Arm machine，也只覆盖 Arm 硬件的一小部分；
- QEMU 的 STM32 官方板型集中在部分 F1、F2、F4、L4 型号；
- 部分板型的 SPI、I²C、GPIO、Timer 等外设仍可能未实现。

**便捷性评价**

- 目标恰好有官方板型：安装和命令行启动较直接；
- 只验证启动、CPU 指令、异常和串口/半主机输出：很好用；
- 验证具体厂商外设驱动：经常会卡在模型覆盖上；
- 自己补 QEMU machine 或 peripheral model 的成本通常高于 Renode 平台描述。

**适合**

- Bootloader（引导程序）、内核、系统启动；
- 有官方 machine 支持的开发板；
- 批量无界面运行、GDB 调试和 CI；
- 不高度依赖具体芯片外设的固件。

### 3.4 Arm FVP / Arm Virtual Hardware

FVP（Fixed Virtual Platform，固定虚拟平台）是 Arm 提供的功能准确模型。AVH（Arm Virtual Hardware，Arm 虚拟硬件）是围绕虚拟目标、工具和云端流程形成的方案。

**特点**

- 提供 Cortex-M0、M0+、M3、M4、M7、M23、M33、M52、M55、M85 及 Corstone 参考平台模型；
- 可作为独立程序在 Windows/Linux 运行；
- 能接入 Keil、命令行和 CI/CD；
- 对 Arm CPU 指令、异常和参考子系统的可信度较高。

**限制**

- 参考平台模型不等于某一款 STM32、NXP 或 GD32 芯片的全部外设；
- 需要 Arm User-based License（用户许可证）。官方说明评估或非商业场景可激活 MDK Community Edition，商业使用需相应产品许可；
- 更适合 Arm 生态和参考平台，不适合非 Arm MCU。

**适合**

- Cortex-M 架构相关代码、CMSIS、TF-M 和 Corstone 平台；
- 希望使用官方 Arm 模型进行自动化验证；
- 已使用 Keil MDK 的项目。

### 3.5 Keil µVision Simulator

**特点**

- 在项目中选择器件后，可直接把 Debug Driver 切换为 Simulator；
- 支持断点、寄存器、内存、调用栈及部分周期级行为；
- 对受支持器件可以模拟 GPIO、ADC、UART、I²C、SPI、CAN、Flash 等片上外设；
- 通过 VTREG（Virtual Target Register，虚拟目标寄存器）和 Debug Function 注入数字、模拟或通信输入。

**便捷性评价**

- 已经是 Keil 工程且器件支持完整：非常方便；
- 适合交互式调试，不需要搭电路；
- 不同芯片的模拟能力并不一致，必须查看器件数据库和 Peripheral 菜单；
- 通信协议模拟的是逻辑和时序行为，不代表物理引脚波形和电气行为；
- 自动化和跨平台性不如 Renode/QEMU。

### 3.6 MPLAB X SIM

**特点**

- 集成在 MPLAB X IDE 中，覆盖 PIC、AVR、SAM 和 dsPIC 系列中的部分器件；
- 支持指令执行、寄存器/引脚刺激、Trace（执行跟踪）、代码覆盖率和数据提取；
- Stimulus GUI 可配置一次性或周期输入；
- 复杂场景可以使用 SCL（Stimulus Control Language，刺激控制语言）。

**便捷性评价**

- Microchip 项目中切换到 Simulator 即可，上手方便；
- 不需要绘制电路；
- 官方明确提示并非所有器件和外设都受支持，实际采用前必须查对应器件的 Simulator Peripheral Support；
- 更适合 CPU 和基础外设代码，复杂外设仍可能需要真机。

### 3.7 IAR C-SPY Simulator

**特点**

- 完全集成在 IAR Embedded Workbench；
- 支持指令级模拟、内存验证、中断模拟、断点及部分代码覆盖/Trace；
- 某些器件使用 IAR 驱动，另一些使用 Imperas Instruction Set Simulator（指令集模拟器）。

**限制**

- 官方说明其外设模拟有限，主要适合不大量依赖外设的程序逻辑；
- 并非 Cycle Accurate（周期精确）；
- 模拟执行明显慢于真机；
- 适合已经购买并使用 IAR 的团队，不适合作为独立通用方案采购。

### 3.8 Ceedling + Unity + CMock

这不是 MCU 模拟器，而是嵌入式 C 的主机测试方案。

**特点**

- Unity 提供断言和测试执行；
- CMock 根据头文件自动生成 Mock（模拟函数）；
- Ceedling 统一完成编译、运行、覆盖率和报告；
- 可以把 GPIO、ADC、Flash、时间和通信驱动替换为可控的 Mock；
- 每次改代码后可在数秒内运行大量测试。

**为什么值得作为底座**

即使拥有整机仿真器，也不应该把所有逻辑验证都压在整机仿真上。整机测试通常更慢，而且失败后定位更困难。将业务逻辑与 HAL（Hardware Abstraction Layer，硬件抽象层）分离后，主机测试可以覆盖：

- 传感器输入对应的控制决策；
- 状态机转换；
- 超时、重试和错误恢复；
- 协议包解析；
- 外设函数是否按正确顺序和参数被调用。

**限制**

- 不执行目标 CPU 指令；
- 不验证链接脚本、启动文件、中断控制器和真实寄存器；
- 如果原代码直接到处读写寄存器，首次改造成可测试结构需要一定投入。

### 3.9 Zephyr native_sim

**特点**

- 将 Zephyr 应用、内核和库一起编译为普通 Linux 可执行程序；
- 可以直接使用 GDB、Sanitizer（运行期检测器）和测试框架；
- 运行速度快，适合应用逻辑和 Zephyr 子系统测试；
- 提供部分 UART、Ethernet、Display 等主机化外设。

**限制**

- 官方明确说明它不模拟特定 CPU 或 SoC（System on Chip，片上系统）；
- 只适合与硬件充分解耦的代码；
- 在当前 Windows 环境中通常需要 WSL2（Windows Subsystem for Linux 2）或 Linux CI，体验不如原生 Windows 工具。

## 4. 不优先推荐的方案

### Proteus、SimulIDE、Tinkercad Circuits

这些工具偏向“先搭电路，再加载固件并观察器件”的交互模式。它们在教学、电路联调和可视化方面有价值，但与本次“不要自己画完整电路”的核心诉求不匹配，因此不作为首选。

### 只使用 IDE 的寄存器窗口

寄存器窗口适合调试，却不等于自动验证。若每次都靠人工观察 LED 状态、串口文本或变量值，回归效率仍然很低。无论选哪种仿真器，都建议让程序输出可机器判断的结果，并通过脚本检查。

## 5. 推荐落地方案

### 路线 A：追求最快看到运行结果

适用：ESP32、RP2040、Arduino、Wokwi 支持的 STM32。

1. 保留现有构建系统，生成 ELF/BIN/HEX；
2. 安装 Wokwi VS Code 扩展；
3. 建立仅包含 MCU 的最小配置；
4. 启动仿真并观察串口；
5. 使用 Scenario（场景）注入按键或外设输入；
6. 使用 CLI 检查预期文本，并逐步接入 CI。

预期体验：首次配置较少，后续通常是“编译—启动—看输出”。

### 路线 B：追求可扩展的固件级自动验证

适用：Zephyr、FreeRTOS、STM32、RISC-V、多节点或长期项目。

1. 在 Renodepedia 或 Renode 自带平台中确认目标板；
2. 建立 `.resc` 启动脚本；
3. 直接加载现有 ELF；
4. 先验证 UART、启动和任务运行；
5. 使用 Robot Framework 写输入与断言；
6. 只有确实缺失时才增加 `.repl` 或外设模型。

预期体验：首次配置高于 Wokwi，配置完成后重复运行和 CI 体验更好。

### 路线 C：追求每天都能快速回归

适用：所有 C 项目。

1. 将算法、状态机和协议处理从寄存器操作中分离；
2. 为 GPIO、ADC、Timer、Flash 等建立 HAL 接口；
3. 用 Ceedling + Unity 建立测试；
4. 用 CMock 替换 HAL；
5. 在 PC 上运行边界、错误和状态转换测试；
6. 再选择 Wokwi/Renode 运行少量固件级场景。

这是整体投入产出比最高的方式：大量逻辑由快速主机测试兜底，少量硬件相关路径交给整机仿真和真机。

## 6. 按目标平台选择

| 目标平台 | 首选 | 备选 | 说明 |
| --- | --- | --- | --- |
| ESP32 | Wokwi | QEMU（特定场景）/主机测试 | Wokwi 对 ESP32 型号和 ESP-IDF 集成较完整 |
| RP2040 / Raspberry Pi Pico | Wokwi | 主机测试 | 快速交互和常用外设体验较好 |
| Arduino AVR | Wokwi | SimulIDE/Proteus | 若不想搭电路，Wokwi 更直接 |
| STM32 | 先查 Wokwi 型号；否则 Renode | Keil、QEMU、Arm FVP | “支持 Cortex-M”不等于支持具体 STM32 外设 |
| Microchip PIC/AVR/SAM/dsPIC | MPLAB X SIM | Wokwi（部分 AVR） | 先查具体器件和外设支持表 |
| 通用 Cortex-M 参考平台 | Arm FVP | QEMU、Renode | 适合内核、异常和架构层验证 |
| RISC-V MCU | Renode | QEMU、IAR | 具体 SoC 模型覆盖决定可用性 |
| Zephyr | native_sim + Renode | Wokwi、QEMU | native_sim 验证应用，Renode 验证固件级行为 |
| 与芯片无关的 C 逻辑 | Ceedling/Unity/CMock | 自建 PC 测试程序 | 最快、最稳定、最易加入 CI |

## 7. 采用工具前的检查清单

不要只检查“CPU 内核是否支持”，应逐项确认：

- 精确 MCU 或开发板型号；
- Flash/RAM 地址和大小；
- NVIC（Nested Vectored Interrupt Controller，嵌套向量中断控制器）；
- 实际使用的 UART、SPI、I²C、CAN、USB、Ethernet、ADC、PWM、DMA；
- 外部 Flash、传感器、显示器和网络模型；
- 固件格式及启动方式；
- GDB、串口输出和自动断言能力；
- Windows 是否原生支持；
- 离线运行、固件上传和许可证要求；
- 仿真模型是功能准确、周期准确，还是只有指令集准确。

只要核心外设缺一项，就应降低对整机仿真结果的信任等级。

## 8. 最终建议

在尚未提供具体 MCU 和框架的情况下，推荐优先级如下：

1. **先用 Wokwi 做一次低成本试跑**：它最符合“代码驱动、少搭电路、快速看结果”；
2. **若型号不支持或需要复杂 RTOS/自动化，改用 Renode**；
3. **若只关心 Cortex-M 内核和参考平台，使用 Arm FVP 或 QEMU**；
4. **若已有 Keil/MPLAB/IAR 工程，先试 IDE 内置 Simulator，避免重复搭建工具链**；
5. **无论选择哪个整机仿真器，都应补上主机单元测试**。

真正决定工具选择的最小信息是：

- MCU 完整型号；
- 使用的 SDK/RTOS；
- 必须验证的外设；
- 期望观察的结果形式，例如串口文本、GPIO 波形、内存值或网络数据。

拿到这些信息后，才可以从“工具调研”收敛为一套可直接运行的仿真模板。
